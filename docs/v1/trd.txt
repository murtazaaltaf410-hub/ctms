Live location pipeline

A driver position reaches student screens in five steps, targeting under 5 seconds end to
end.

  1. The driver app reads GPS in a foreground service and stores each fix locally with a
     timestamp.

  2. Every few seconds it sends the unsent fixes as one batched POST
     /trips/{id}/locations .

  3. The server validates the fix, updates the bus's in-memory state and queues it for
     batched writing to PostgreSQL.

  4. The server pushes the new position and status to all /ws/live subscribers.
  5. The student app moves the bus marker smoothly to the new position and shows a

     "last updated" time.

ETA and nearby-alert algorithms

ETA to a stop

The server never calls Google per ETA. It stores each route polyline with a cumulative
distance for every point, then:

  1. Snaps the bus to the nearest polyline point, searching only forward from its last
     snapped point so loops and parallel roads do not cause jumps.

  2. Takes the remaining distance to the stop as the stop's cumulative distance minus the
     bus's cumulative distance.

  3. Smooths speed with an exponential moving average over about the last 60 seconds of
     fixes.

  4. Divides, using a minimum speed so a stationary bus does not give an infinite ETA.

  ETA = \frac{d_{stop} - d_{bus}}{\max(v_{smooth}, v_{min})}

If the stop is already behind the bus on this trip, the app shows "passed" and the next
scheduled departure when a timetable exists. Starting value for the minimum speed is 10
km/h; tune it from field data.

Nearby alert

With alert mode on, the student app sends its location only after moving a meaningful
distance (starting value 100 m) and at least once every few minutes. On each bus position
update the server checks active buses against students who have recent locations.
An alert is sent only when all of these hold:

     The straight-line distance between the student and the bus is under 500 m (stored as
     a setting, not hard-coded).
     The bus is on an active trip and its last fix is under 30 seconds old.
     The student's last location is under 5 minutes old and its accuracy is better than 100
     m.
     The bus is getting closer, meaning its distance to the student decreased over the last
     two fixes.
     No alert has been sent to this student for this bus on this trip (checked in
      alert_log ).
A bounding-box test runs before the exact distance calculation so only nearby students
are measured. The alert text names the bus and route, for example "Bus 2 (North Campus
route) is about 400 m away".

Security, authentication and data retention

Authentication and authorisation

     Students and admins: the app signs in with Google and sends the Google ID token;
     the server verifies it and issues its own short-lived access token plus a refresh token.
     Drivers: phone number + OTP; the server accepts only numbers an admin has already
     registered and linked to a bus.
     Admins: a Google account counts as admin only if its email is in the admin list in the
     database; the first admin is seeded manually.
     Roles: every endpoint declares the roles allowed; the role is read from the database,
     not trusted from the token alone.
     Ownership rules: a driver can only post positions for their own bus's active trip; a
     student can only read and write their own account and location.

Protection

     HTTPS everywhere; no secrets in the app. Server secrets live in environment variables
     on the host.
     Google Maps keys restricted by app signature and by API; the Directions key stays on
     the server only.
     Rate limits per user and per IP, with tighter limits on OTP requests and location
     uploads.
     Input validation on all coordinates (range, accuracy, speed) and all admin text.

Database growth estimate (assumes 3 buses running 10 hours a day, which you should
replace with the real timetable): one fix every 4 seconds gives about 27,000 rows a day, or
about 2.4 million rows over 90 days. Keeping history at one fix per 10 seconds cuts that to
about 1 million rows, roughly on the order of 100 MB with indexes (approximate).

Scaling path beyond the pilot: move to a paid always-on instance; add Redis pub/sub so
several server workers share live positions; use PostGIS for proximity queries; partition
the locations table by month; add a web admin dashboard.
